01起点：一个困惑

AI 工具很多，但总觉得没有真正用到位

过去一年，AI 工具层出不穷。多数产品经理都在尝试——ChatGPT 写文档、Cursor 写代码、接 API 做自动化。但始终有一个感受：没有真正用到位。

以 OpenClaw 为例。上线时非常火，但排行榜上最热门的 Skill：

排名Skill功能
1Document Summarizer总结文档
2Exa Search搜索增强
3Weather查天气
4Image Generator生成图片
5Translator翻译

看着不兴奋。总结文档不是刚需，查天气不需要 AI。技术上都能跑通，但没人真正为输出买单。OpenClaw 很快冷了——大部分人没有真实场景。

02转折：从 Demo 到真实场景

用不好 AI 的原因不是工具不行，是没有给它真实的工作场景

"The best AI use cases come from real workflows, not demos."
没有场景 → 输出可有可无 → 不会认真调优 → 永远停在浅层 有场景 → 输出影响工作质量 → 认真投入 → 越用越深 → 形成飞轮

现阶段最好的场景，就是自己的日常工作。沿着这个方向，开始系统性地思考：产品经理的工作流中，哪些环节可以让 AI 深度参与。

03产品经理的工作循环

一个不断迭代的循环，每个环节都有 AI 介入的空间

┌──────────────────────────────────────────────────────────────────┐ │ │ 需求发现 → 调研 → 方向决策 → 产品定义 → 设计 │ ↑ ↓ │ │ 信息同步 进度跟踪 │ │ │ 复盘 · 知识沉淀 │ │ │ ↓ │ 迭代方向 ← 效果度量 ← 上线 ← 交付 ← 验证 ← 评审对齐 │ └──────────────────────────────────────────────────────────────────┘

每个环节在传统模式下都有明确的依赖：调研靠研究团队，理解实现靠研发，定 eval 靠算法，出原型靠设计，验证方案靠排期。

过去几个月，沿着这个循环逐一探索：哪些环节可以用 AI 实现更高程度的独立闭环。

06深入：让 AI 读代码

直接影响了核心功能的产品定义

背景：AI 摘要功能从模板化转向标准化，第一步是搞清楚线上版本做了什么。传统做法是找研发问，但每人只熟悉自己的模块，拼出的全貌是碎片化的。

做法：直接让 AI 读线上核心模块的完整代码——3 步 pipeline：Framework → Section Extraction（并行）→ Polish。

关键发现一：两个版本方向根本不同

线上版本新方向
本质Prescriptive — 有"正确"结构，系统去逼近Descriptive — 没有"正确"结构，只有"忠实"的结构
"好"的标准MECE + 文学可读性Recall 对齐 + 事实可信度
信息处理按类型分类提取，再重组为叙事按主题归类，不预设类型

这意味着新方向不是在原有基础上"调优"，而是需要部分重新设计。

关键发现二：可复用的好设计

可复用

Action Items SMART 过滤

Specific + Measurable + Assignable，和新定义的"三重测试"本质等价
可复用

完备性检查

每条信息必须有归属，逻辑可沿用到新架构的"Step D 查漏"

关键发现三：不该做什么

线上版本 retrieve 行业最佳实践模板来组织结构——对"专业呈现"方向合理，但和"事实还原"方向不兼容。"Excellent Literary Readability" 作为显式顶层目标，在新方向下需要让位给事实可信度。

💡
这份分析直接改变了后续讨论的方式。不再是"我觉得应该这样改"，而是 "代码现在是 A，我们要往 B 走，这些具体的点可以复用，这些需要调整"。

07深入：方案自动验证 — Auto Research

收获最大的探索，也是 token 消耗最多的方向

灵感来自两个方向：Karpathy 的 "Evals are all you need"——先定义"什么是对的"，再去优化；以及 Darwin.evals 项目，用达尔文进化论方式优化 prompt。

1

并行研究

AI 多维度并行调研，搞清楚"好"的标准。不能一上来就让机器进化——需要先确定方向。

2

数据验证

用真实生产数据验证框架。研究产出可能对，也可能是一厢情愿。

3

定义 Eval

把"好"拆成可打分的维度 + 评分标准。没有 eval 就没有进化。

4

自动迭代

AI 生成 → 评测 → 分析失分 → 改 prompt → 下一轮。找到天花板和真正的瓶颈。

核心转变：工作重心从"调 prompt"变成"定义什么是好的"。后者才是产品经理的核心价值。

08深入：PRD 录音驱动迭代

从触发事件到 PRD 落地的完整链路——不只是编辑文档，是把变更上下文转化为具体修改

传统方式
开评审会 → 手动记意见 → 手动改 → 下次评审发现上次漏改 → 关联文档忘了同步
改造后
触发事件 → AI 自动收集上下文 → 对比 PRD 逐条识别改动点 → 用户确认 → 精准修改 + 高亮 → 关联文档检查 → 版本管理

完整的 6 步流程

触发事件（评审会 / 群聊讨论 / 竞品发现 / 自己的想法） ↓ Step 1 收集变更上下文 录音 get_note / 群聊搜索 / 竞品文档 / 用户描述 ↓ Step 2 读取当前 PRD 提取：版本号 + 文档结构 + 近 3 条 Change Log ↓ Step 3 识别改动点 → 强制对照检查 每条候选改动必须回答： ① PRD 里是否已有？ ② 是否在本 PRD scope 内？ ↓ Step 4 用户确认 → 执行修改 block 级精准替换（old_str → new_str） 新内容加 orange_bg 高亮，旧高亮清除 ↓ Step 5 关联文档检查 改了产品定义 → 评测标准需同步？ 改了信息架构 → 交互文档需同步？ ↓ Step 6 更新 Change Log

关键设计：强制对照检查（Step 3）

这一步是避免"改了又改、改重了、改错地方"的核心。对每条候选改动：

检查一

PRD 里是否已有？

上一版可能已经写了。如果已有，标注"不需要改"并说明在哪个章节，避免重复改动。
检查二

是否在本 PRD 的 scope 内？

同一话题可能涉及多个文档——放量策略不属于功能 PRD，排期不进产品定义。不在 scope 内的标注"属于其他文档"。

多种触发源自动适配

用户说AI 怎么收集上下文
"基于今天评审的反馈"搜索今天的会议录音 + 相关群聊讨论
"基于竞品分析结论"读取最近的竞品分析文档（memory 或 docs/）
"基于群里的讨论"搜索相关群聊消息
"我想改 XX 部分"用户有明确想法，直接进入对比

核心原则

原则

不替用户做产品决策

角色是"把决策落到文档里"，不是"决定应该怎么改"。矛盾意见列出来让用户判断。
原则

高亮即本轮变化

新增/修改加 orange 高亮，上一版高亮清除。研发收到文档只看高亮部分，changelog 即历史脉络。
原则

关联文档不能忘

改了产品定义 → 评测标准的维度/权重可能需同步。改了功能范围 → Roadmap 的 DoD 可能需更新。

核心 PRD 就是这样迭代的——13 天，v0.1 到 v0.7，最密集一天 4 轮。目前已沉淀为标准化 Skill，覆盖多个核心 PRD 文档的自动化迭代。

10深入：企业 IM 聊天记录集成

最近新增的能力——让 AI 直接读取企业 IM 群聊和单聊消息

录音能捕捉会议上说了什么，但大量工作讨论发生在企业 IM 群聊里——临时决策、任务分配、方案讨论。这些信息以前只能靠人翻聊天记录。现在 AI 可以直接读取。

三种操作模式

搜索群

find_chat

按群名关键词搜索，获取群 ID。比如搜"产品核心群"就能找到对应的群。
列出消息

list

列出某个群/单聊的最近消息。支持时间范围和分页。
全局搜索

search

跨所有群搜索——关键词、发送者、时间范围、@我。一条命令找到散落各处的讨论。

焦点图谱：关注什么群、关注什么人

不是所有群都值得 AI 关注。焦点图谱按团队组织了当前重点：

产品团队 A

核心 + 研发 + 评测

核心对齐群、站会群、功能 Demo 群、算法优化群、评测沟通群……
产品团队 B

核心 + 研发

核心对齐群、系统架构群、评测群……

三条自动化链路

A

im-digest · 每晚自动沉淀

22:50 按焦点图谱扫描当天消息 → 过滤闲聊 → 提取 [决策] [行动] [风险] [讨论] [@我] [数据] → 写入 memory，23:00 由 memory-extract 进一步结构化。

B

reply-assist · 自动代回消息

每 5 分钟扫描 @我 的新消息 → 生成上下文摘要和回复草稿 → 以交互卡片推送（带发送/跳过按钮）。涉及承诺的消息不会自动发送，必须人工确认。

C

主动调用 · AI 自己决定什么时候读群聊

写周报时 → 自动拉取团队群一周讨论。写 PRD 时 → 搜索相关话题在群里的讨论脉络。准备 1:1 前 → 拉取对方近期消息。不需要用户说"去搜群聊"，AI 自己判断需要。

💬
效果对比：以前写周报靠回忆 + 翻群聊，容易漏掉非正式渠道的决策。现在 AI 自动从焦点群里搜集素材，周报覆盖率显著提升——很多"群里聊了但没上会"的决策不再被遗漏。

11踩过的坑

都是在探索 AI 边界的过程中踩出来的真实教训

教训

"好"的定义本身就很难

Memory 抽取优化——什么算"好的记忆提取"，团队到现在还在讨论。没有共识的标准，自动迭代根本跑不起来。
教训

上下文不完整，效果就差一截

系统接入了录音、文档、代码，但 IM 群聊等上下文还没覆盖。很多时候不得不手动补充背景信息。

过度信任 AI 的判断

12几点体会

最重要的变化不是效率，是协作模式

1

做到以前做不到的事，比想象中容易

读代码理解架构、跑十几轮自动实验、产出技术级竞品分析——以前要么做不了，要么需要跨团队协作几周。现在一个 PM + AI，几天就能完成。

2

Context 比 Prompt 重要

Prompt 决定一次对话的质量，Context 决定 AI 对工作的理解深度。后者回报高一个数量级。与其用文字描述问题，不如直接给 AI 真实素材。

3

变化最大的不是效率，是协作模式

以前：PM 提需求 → 等排期 → 几周一个循环。现在：PM 自己定义 eval、跑实验、定位瓶颈，带着量化结论和可交付 spec 找研发。

4

系统比单次对话重要

没有什么 prompt 黑科技。真正有效的是把工具和流程串成一个持续运转的系统——session 管理、memory 积累、context 自动加载。串起来后产生复利。

5

使用 AI 的三个阶段

① 不知道怎么用 → ② 刻意思考"这件事能不能用 AI" → ③ 更自然地使用 AI。从 1 到 2 需要主动意识，从 2 到 3 需要足够多的真实使用积累。

13实用技巧

三个可以今天就开始做的事

连 MCP，让 AI 直接访问工作素材
与其复制粘贴内容给 AI，不如让它直接连接数据源。体验差距非常明显——AI 从"你告诉它什么它才知道"变成"它自己能看到"。

让 AI 帮你规范化重复操作
如果一件事做过 3 次以上，就值得让 AI 帮你沉淀成 Skill SOP——定义清楚输入格式、处理步骤、输出规范。

选一个对自己重要的 Skill，尝试自己优化它
选一个对你最重要的（竞品调研、会议纪要、周报...），花时间定义"好的输出长什么样"，然后让 AI 按标准自评和改进。一旦有了标准，迭代速度会快很多。
